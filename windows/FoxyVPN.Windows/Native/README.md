# Windows native tunnel runtime

The Windows VPN core uses the upstream **HEV socks5 tunnel 2.17.1** C API, which is the same native tunnel engine pinned by the Android Gradle build. The CI workflow builds that exact tag using MSYS2 and bundles its shared-library dependencies beside the WPF executable.

The workflow separately downloads the official **Wintun 0.14.1** x64 distribution from `https://www.wintun.net/builds/wintun-0.14.1.zip`, verifies its published SHA-256 (`07c256185d6ee3652e09fa55c0b673e2624b565e02c4b9091c79ca7d2f24ef51`), then requires a valid Authenticode signature whose signer identifies WireGuard LLC before copying `wintun.dll`. The signed DLL is a runtime dependency, not generated by this repository.

The current proxy relay implements DNS-only SOCKS5 UDP ASSOCIATE: it attempts DoH by opening a TCP CONNECT stream to a known resolver IP's port 443, validates the nested TLS certificate, then falls back to DNS-over-TCP through authenticated CONNECT. Non-DNS UDP/QUIC is dropped because the available edge protocol provides TCP CONNECT only. The relay and its deterministic fake-upstream tests are source-only at this point; neither the tests nor the nested TLS/DoH sequence has been run against the real service because .NET SDK/MSBuild is unavailable here.

Native binaries are build artifacts and are intentionally not committed to this source tree. A local WPF build without the native build step remains in preflight-only mode. See `windows/README_WINDOWS.md` and `PHASE_1_6_HEV_NATIVE_CORE_REPORT.md` for remaining integration gates.

Upstream code and licenses:
- HEV: https://github.com/heiher/hev-socks5-tunnel (MIT; pin `2.17.1`)
- Wintun: https://www.wintun.net/ (official signed runtime distribution; pin `0.14.1` and verify the SHA-256 above)


## Phase 1.7 current integration

The WPF source registers the HEV runtime as part of `WindowsSystemTunnelRuntime`. It starts only after the authenticated HTTP/2/localhost SOCKS layers are alive and stops after the system-route transaction has been restored. The Windows CI pipeline is responsible for building the pinned x64 native library and bundling signed Wintun; those native artifacts have **not** been produced or executed in this authoring environment. A native DLL's presence alone is not proof of a working tunnel.


## Phase 1.8 lifecycle behavior

The full runtime monitors network-address/availability and Windows suspend/resume events. It refreshes the journaled physical-egress guard for new/renamed active adapters and faults closed if the original transport local address is no longer assigned. Guardian proxy-pass renewal refreshes the shared provider cache for future HTTP/2 CONNECT streams. Neither behavior has yet been verified under real Windows network handovers or live Guardian sessions.
